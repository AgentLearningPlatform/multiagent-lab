# 软件缺陷管理本体 · 建模说明

> 示例本体建模说明（REQ-90 ②）。seed-learning key=defects 一键灌装。

## 背景与目标

演示 **AI 生成路径**（REQ-82）的产物形态：CQ 驱动 + 生成-校验循环。该示例的 spec_json 由「AI 创建」链路生成后人工校订入库，作为学习者对照自己 AI 草稿质量的"参考答案"。

## 目标 CQ 列表

1. 某缺陷源于哪个需求？（originated_from）
2. 某需求关联了哪些缺陷？（反向查询）
3. 某模块的缺陷都有哪些严重级别？（属性过滤）
4. 某缺陷阻塞了哪些其他缺陷？（blocks）

## 建模决策记录

| 决策 | 理由 |
| --- | --- |
| Requirement / Defect / Module 三概念 | 最小闭环即可回答全部 CQ |
| originated_from / blocks 两个关系 | 覆盖"溯源"与"传导"两类典型查询 |
| severity / status 作为实例属性 | 演示 attributes 在查询返回中的形态 |
| Defect 不设 Bug/FeatureRequest 子类 | 保持精简；子类层次是学习者的扩展练习 |

## 局限与反例

- **无人员概念**：真实缺陷库应有 Assignee（可对照 FOAF:Person 复用，见方法论模块三）。
- **blocks 无环约束**：A 阻塞 B、B 又阻塞 A 的环不会被校验拦截——SPARQL 型方案精确匹配不查环，这是"校验能拦什么/不能拦什么"的好反例。
- **严重级别用字符串**：真实系统应建模为枚举概念（SKOS 分类），见设备故障示例的分类体系。
