# 示例 5 · 设备故障知识库 → 设备故障本体（O13 / D-O14 / REQ-108）

**学习目标**：补齐「文本 → 三种语义资产形态」对照的最后一块——同一份语料，在
RAG 子模块里是检索片段，在 GraphRAG 子模块里是 KG，在构建平面里是本体（spec_json）。

## 演示步骤

1. **建知识库**：「知识库」栏新建两个库——`设备故障知识库-RAG`（mode=rag）与
   `设备故障知识库-GraphRAG`（mode=graphrag）。
2. **灌语料**：把本目录 `device_fault.kb.md` 全文粘贴导入两个库（内容相同，便于对照）。
   GraphRAG 库导入时若 semantica worker（:8093）在运行会自动抽取 KG。
3. **进入第六路径**：「本体构建」栏 → 第 6 项「由知识库构建」（部分可用徽标）。
   KB 选择器会显示两个库的 mode 徽标与 chunk/KG 规模。
4. **三种策略对照**（04 §3.7）：
   - **策略 A（chunk→LLM）**：选 RAG 库 → CQ 选「自动生成」或自定义（如"某故障源于什么原因？某原因对应什么维护措施？"）→ 生成草稿。观察 LLM 的抽象能力（概念命名、层级归纳）。
   - **策略 B（KG→直转）**：选 GraphRAG 库（无 KG 时点「构建 KG」）→ 生成。观察规则抽取的保真度边界——`entity→Concept`、`IS_A→parents`、`HAS→具有`。
   - **策略 C（混合）**：选 GraphRAG 库 → 生成。KG 初稿 + LLM 补全 definition，对照 B 看补全了什么。
5. **入库对照**：任一策略「创建并保存到本体资产」后，与内置示例
   **设备故障知识**（`failure.json`，Open Ontologies 卡的 SKOS 分类演示本体）对照：
   人工建模的层级/互斥与自动抽取的差距就是学习点。
6. **闭环验证**：入库的本体导出 TTL → semantica 摄取；或部署 SPARQL 型运行方案，
   在工作台验证「散热不良 → 引起 → 过热停机」类查询能命中。

## 注意

- 策略 A/C 需要「设置-模型管理」里启用中的 chat 默认连接。
- 策略 B/C 需要 semantica worker 在运行；worker 不可达时按 M14 降级语义提示，不阻断。
- 生成侧校验报告只是快照，入库时构建平面 `PUT /api/ontologies/{id}/spec` 仍会做权威校验。
