## 0. 背景与目标

eino-multiagent-lab 是学习型 Web 平台，功能分**智能体**与**本体**两类。本体模块目标：支持**导入、创建、编辑、浏览**多个本体，并以后台**多套运行方案**的形式运行本体，供智能体对话结构化查询。

两条架构级原则（主人 2026-09-20 拍板）：

1. **构建与运行解耦**：本体仓库是唯一事实源；运行平面支持同时启动多套本体运行方案，方案停止/删除不影响仓库资产。
2. **开源优先**：各子系统优先使用现成开源方案，避免重复造轮子；自研边界由方案文档 §6 明确。

## 2. 功能需求

### 2.1 本体资产管理（构建平面 · 仓库）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| REQ-60 | **本体列表页（类知识库形态）**：列出全部本体（名称、简介、概念/关系/实例统计、版本、更新时间）；支持查询搜索、新建（名称+简介）、重命名、删除（二次确认）；本体为全局资源，可被任意对话的运行方案加载 | P1 |
| REQ-80 | **导入外部本体并直接加载运行**：①支持上传/粘贴外部文件，格式分层：`spec`（自家格式，无损）/ `csv`（nodes+edges 两表）/ `graphml`（通用图交换）/ **OWL-RDF/Turtle（有损导入，P1）**；②导入产生**多形态资产**——原始文件原样存档 + 归一化 spec_json + 导入报告（统计/warnings/有损映射说明）；③导入成功的本体立即可被任意运行方案加载运行 | P1 |
| REQ-69 | **OWL/RDF 有损导入映射**（REQ-80 的 OWL 分支细则）：`rdfs:label`→名称、`rdfs:subClassOf`→继承关系、`owl:NamedIndividual`+`rdf:type`→实例、对象属性断言→实例关系；公理/推理语义丢弃并计入导入报告；映射细则用 ontologies/ 三个真实本体（K8s/FLUIDOS/HOCC）验证后定稿 | P1（v0.5 时为 P2，随 REQ-80 提级） |
| REQ-72 | **导入体验**：导入前预览解析结果（概念/关系/实例数量统计、映射规则、无法识别条目的 warnings）；导入失败给出可读错误；导入成功的新本体 version=1，立即可在列表/运行方案配置中使用 | P1 |
| REQ-62 | **内置示例本体**：一个最小 K8s 运维本体（Pod/Node/Service 概念、belongsTo/exposes 关系、若干实例），seed 方式提供，便于上手 | P1 |
| REQ-83 | **基于已有本体编辑扩展为新本体（fork）**：本体列表页「复制为新本体」→ 复制全部形态资产（记录 fork 来源）→ 编辑扩展后作为独立新本体保存 | **P2** |
| — | **导出**：本体可导出为 spec_json（备份/分享）；RDF 型本体可导出原始形态；**从零创建的本体（仅有 spec_json）可经 spec_json→Turtle 转换导出 RDF 形态**，使其可在 SPARQL 型运行方案中加载运行 | P1（转换器随 O1 交付，由 Python rdflib sidecar 实现——v0.4） |

### 2.2 本体创建与编辑

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| REQ-61 | **JSON 编辑器**：本体内容用约定 JSON 表达三类要素 `concepts`/`relations`/`instances`；页面提供结构化 JSON 编辑器（带格式校验） | P1 |
| REQ-63 | **保存校验**：JSON Schema 结构校验 + 引用完整性（引用了未定义概念/关系时给出错误），不允许保存坏本体；校验在构建平面服务侧完成 | P1 |
| REQ-64 | **只读预览**：编辑页支持概念/关系/实例分栏只读预览，不只是原始 JSON | P1 |
| REQ-71 | **图形化编辑器（P1 增强）**：React Flow 画布（节点=概念/实例、连线=关系）+ RJSF 属性表单，与 JSON 编辑器双形态并存、可切换；保存时画布数据经适配器转回 spec_json，校验不变 | P1 |
| REQ-82 | **LLM 辅助从零创建**：①入口「AI 创建」：自然语言描述领域（可附参考示例/规模要求）→ 生成本体草稿；②生成走**结构化输出 + 服务端校验循环**（校验失败错误回喂模型修正，最多 3 轮），**草稿必须经用户预览确认后才入库**，不自动保存；③模型能力经主平台代理提供（模型能力归主平台，校验归构建平面） | P1 |

### 2.3 本体可视化浏览

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| REQ-81 | **交互式可视化浏览**：①本体详情页提供浏览入口，支持查看**类层次与对象属性结构**（TBox）和**实例间关系**（ABox）两类视图；②**直接评估并嵌入开源方案**（不做通用图渲染自研）——选型评估与集成方式由方案文档 §3.5 给出（当前结论：TBox→WebVOWL，ABox→按运行方案类型路由 LodLive/OntologyExplorer 资产）；③浏览对象是"运行中的本体"，与运行方案联动 | P1 |

### 2.4 本体运行方案（运行平面）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| REQ-84 | **运行方案管理界面（列表）**：列出所有后台运行方案——名称、运行时类型、已加载本体、状态（running/stopped/error 等）、端口/端点、健康信息；支持启动/停止/删除（二次确认）；状态自动刷新；可查看方案最近日志 | P1 |
| REQ-85 | **运行方案配置**：新建/编辑运行方案——①选择**运行时类型**（P1 支持 SPARQL 型 Oxigraph，Fuseki 随后交付；轻量内存图为 P2 可选，**直接集成开源引擎、不自研**（D-O5 v0.4）——引擎清单见方案 §4.2）；②勾选加载的**本体集合**（来自构建平面仓库）；③配置**运行细节**（监听端口、推理开关、SPARQL 端点可写性、资源参数等）；配置变更后需重启方案生效，页面明确提示 | P1 |
| REQ-86 | **多套运行方案并存**：后台可同时运行 ≥2 套方案（不同类型/不同本体集合/不同端口），互不干扰；不同对话可分别挂载不同方案 | P1 |
| REQ-87 | **构建/运行解耦原则**（v0.3 调整）：本体仓库为唯一事实源；运行方案是仓库内容的"部署视图"——同一本体可被多套方案加载；方案停止/删除不影响仓库资产；本体在仓库更新版本后需在方案页**显式重载生效**（页面提示，不静默）；P2 可选引擎引入后可再评估"按版本自动生效"对照语义 | P1（架构原则） |
| REQ-88 | **开源优先原则**（v0.4 调整）：每个子系统先评估开源方案再决定自研；自研仅限业务编排与路由薄层（运行方案编排层、MCP facade 路由）；**OWL/RDF 解析不自研（Python rdflib sidecar）、内存图引擎不自研（P2 直接集成开源）**——清单由方案文档 §6 维护 | P1（原则） |

### 2.5 对话集成（与智能体模块的边界）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| REQ-65 | **对话启用本体**：对话配置选择某个**运行方案**（而非直接选本体）；启用后该方案的 MCP 查询工具挂给 Agent，并注入本体使用指引（含 `ontology_id` 上下文） | P1 |
| REQ-66 | **本体查询能力**（经统一 MCP 契约提供，精确匹配优先、不做逻辑推理）：按名称/标识查概念或实例、查某实例的关系（邻居）、列出某概念下所有实例；**该契约对所有运行时类型一致**（SPARQL 型经 facade 翻译，非 SPARQL 型直查，差异由 facade 屏蔽） | P1 |
| REQ-67 | **查询过程可见**：工具调用在对话时间线可见，便于理解 Agent 如何利用结构化知识 | P1 |
| REQ-70 | **连通与生效**：①运行方案管理器可探测各方案健康状态，方案不可达/停止时有明确降级提示、不影响其他方案与普通对话；②本体管理页保存新版本后，按 REQ-87 语义分类型生效；③MCP 连接具备初始化与断线重连 | P1 |
| REQ-73 | **打开即用一致性**：编辑页保存或导入产生的新版本，在运行方案与对话侧按 REQ-70/REQ-87 语义即时可见或明确提示重载，无需重启平台 | P1 |
| — | **边界说明**：对话侧 UI（启用开关、下拉、状态提示 REQ-19b/c/d）与主平台对接实现（MCP Client 接入、双反向代理、模型代理端点——智能体 PRD v0.6 的 REQ-97/98）由**智能体侧文档维护**；本模块负责保证契约能力：统一 MCP facade、按方案 guide 端点、降级事件语义、REST API 可反代 | — |

### 2.6 工具链配置（七阶段流水线，2026-09-20 新增）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| REQ-74 | **七阶段工具链模型**：将本体工程定义为七个阶段——S1 本体来源 → S2 编辑管理 → S3 校验 → S4 可视化 → S5 运行时引擎 → S6 服务化接口 → S7 对接 Agent；每阶段定义输入/输出**交接形态**（spec_json / original / endpoint 三形态契约）；平台现有功能（导入、编辑、校验、Explorer、运行方案、facade）映射为各阶段的**内置默认工具**，功能不变、组织升级。阶段划分与候选清单详见《本体工程七阶段与开源工具链清单.md》 | P1（叙事与映射） |
| REQ-75 | **工具链配置页**：学习者为本体创建工具链配置（pipeline_profile）——每个阶段从候选清单选择工具，保存为配置；支持复制为新工具链、重置为默认（默认工具链每阶段预置 builtin 项，打开即可用）；配置可命名管理 | P2 |
| REQ-76 | **引导执行模式**：非自动编排阶段的工具（guided 模式），平台生成执行指引（安装/启动命令、数据交接点、入口链接），学习者逐项打卡完成并记录状态；运行段（S5）沿用 Runtime Manager 自动编排（managed 模式） | P2 |
| REQ-77 | **候选清单开放性**：各阶段候选工具清单数据驱动维护（增删工具不改核心代码）；新增工具需声明许可、执行模式（builtin/guided/managed）、输入输出形态与学习要点 | P3 |

> **工具链候选登记（v0.5，随 open-ontologies 独立集成引入）**：S1 段增候选「实例数据快速灌装」（open-ontologies `load`：CSV/XLSX/JSON→RDF，guided）；S3 段增候选「语义校验/推理」（open-ontologies `validate`/`reason`，guided）。两条均为 `tools.json` 数据条目（REQ-77 口径），**不新增执行模式**；设计登记见《04_本体_方案设计.md》§4.6/§4.7。

## 3. 非功能需求

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| NFR-O-1 | **一致性**：本体保存后按 REQ-87 分类型生效；同一本体在同一运行方案内查询结果与仓库版本一致（带 version 校验） | P1 |

| NFR-O-4 | **本地化约束**（继承平台定位）：全部服务回环监听、无鉴权、单机运行；运行方案编排以子进程为主，Docker 可选 | P1 |
| NFR-O-5 | **可观测**：方案启停/健康检查/装载事件有日志；方案页可看最近 200 行运行日志 | P2 |
