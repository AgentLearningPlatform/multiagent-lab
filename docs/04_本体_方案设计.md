## 0. 模块定位（v0.2 更新：构建与运行解耦）

**一句话**：本体模块 = **构建平面 + 运行平面**两个解耦的子系统。构建平面负责本体的导入、创建、编辑、浏览（"本体仓库是唯一事实源"）；运行平面支持**同时启动多套本体运行方案**，每套方案可选择运行时类型、加载哪些本体、配置运行细节。Agent 对话经统一 MCP 契约挂载某个运行方案。

**总原则（v0.6 更新）**：各子系统**优先使用现成开源方案，避免重复造轮子**；自研保留运行方案管理器（编排层）与 MCP facade 路由（学习内容本身）——**OWL/RDF 解析不自研，走 Python rdflib sidecar**（O1 引入，同时承担 spec_json→TTL 导出与可选 pySHACL）；轻量内存图引擎**不自研**（D-O5 v0.4：P1 引擎用开源 Oxigraph；P2 若需内存图直接集成开源 Cayley fork，LG-12 自研学习目标取消）。

**七阶段工具链视角（v0.4 新增，D-O7）**：本体工程进一步组织为 S1 本体来源 → S2 编辑 → S3 校验 → S4 可视化 → S5 运行时引擎 → S6 服务化 → S7 对接 Agent 的流水线；每阶段候选主流开源工具可配置（需求 REQ-74~77），执行模式三态——builtin（内置直接用）/ guided（平台给指引+打卡，不拉进程）/ managed（仅 S5，Runtime Manager 自动编排）。阶段清单详见《07_本体_工程七阶段与开源工具链清单.md》，配置层设计见本文 §4.6。**该视角是对现有功能的重新组织 + 一个薄配置层，不引入新子系统。**

**五项操作方式需求（2026-09-20 主人提出）** 已落位为 REQ-80~88 并独立维护于《03_本体_需求文档.md》§1，此处不再重复。

### 2.1 核心数据流

1. **导入流（REQ-80）**：上传文件 → 格式识别 → 原始形态存仓库（OWL/TTL 原样）→ 归一化为 spec_json（可损，生成导入报告）→ 校验 → 入库。**一个本体资产 = 元数据 + 多形态文件**（original + spec_json）。
2. **LLM 创建流（REQ-82）**：描述领域 → Eino 结构化生成 spec_json 草稿 → 构建平面校验 → 错误回喂 LLM 修正（最多 N 轮）→ 用户预览确认 → 入库。
3. **分发流（REQ-87）**：运行方案启动时，从仓库取所选本体的**对应形态**——memory-graph 型取 spec_json；oxigraph/fuseki 型取 original OWL/TTL → 写入运行时数据目录/加载端点。
4. **查询流（REQ-65/66 继承）**：Agent 挂载运行方案 → 经统一 MCP facade 调 onto_* 工具（ontology_id 定位方案内本体）→ Manager 路由到对应运行时（内存图直查 / SPARQL 型转查询）→ 结果 + version 返回。
5. **浏览流（REQ-81）**：浏览页挂在运行方案上——TBox 结构经 WebVOWL（仓库文件直接转换）；实例关系经 LodLive（SPARQL 型方案直连端点）或 OntologyExplorer 资产（memory-graph 方案）。

## 3. 构建平面设计

### 3.1 本体仓库（多形态资产，REQ-87 事实源）

```sql
-- ontology-service/migrations/002_repo.sql（演进自 001）
CREATE TABLE ontology (
  id TEXT PRIMARY KEY,                    -- 如 onto_k8s_ops
  name TEXT NOT NULL,
  description TEXT DEFAULT '',
  version INTEGER NOT NULL DEFAULT 1,
  forked_from TEXT,                       -- REQ-83：fork 来源（P2）
  created_at DATETIME, updated_at DATETIME
);
CREATE TABLE ontology_artifact (          -- ★ 多形态资产：一个本体 N 个形态
  ontology_id TEXT REFERENCES ontology(id) ON DELETE CASCADE,
  format TEXT NOT NULL,                   -- spec_json | owl_rdfxml | turtle | csv | graphml
  content TEXT NOT NULL,                  -- 文件内容（大文件可存盘+路径）
  is_normalized INTEGER NOT NULL DEFAULT 0,  -- spec_json 归一化形态标记
  imported_at DATETIME,
  PRIMARY KEY (ontology_id, format)
);
```

要点：**original 形态不可变**（导入时存档，供 RDF 型运行时原样加载与溯源）；spec_json 是归一化工作形态（编辑/校验/内存图用）；查询统计（概念/关系/实例数）从 spec_json 计算。

### 3.2 导入（REQ-80，整合原 REQ-68/69/72）

流程：上传/粘贴 → 格式嗅探（扩展名 + 内容特征）→ ①原样存 original 形态 → ②解析为 spec_json（分格式解析器，规则沿用 v0.1 §4.3 表格：spec 无损/csv 两表/graphml/OWL-RDF 有损）→ ③校验 → ④入库（version=1）→ ⑤导入报告（统计 + warnings + **有损映射说明**）。

OWL/TTL 导入映射细则（v0.1 开放问题 O-1 已落地为 P1）：`rdfs:label`→name、`rdfs:subClassOf`→继承关系、`owl:NamedIndividual`+`rdf:type`→实例、对象属性断言→实例关系；annotation 属性→attributes（待细则定稿）；公理/推理语义丢弃并计入 warnings。**用 ontologies/ 下三个真实本体做验收集**。

### 3.3 LLM 辅助创建（REQ-82）

- **入口**：本体列表页「AI 创建」→ 填写领域描述（+可选：参考示例、规模要求）→ 生成 → 预览 → 确认入库或继续对话修改。
- **生成闭环（学习目标 LG-14）**：Eino `ChatModel` + 结构化输出（spec_json Schema 约束）→ 构建平面校验器 → 失败则把错误列表回喂 LLM 修正（最多 3 轮）→ 通过后交用户确认。**校验器与人工编辑共用同一套**（REQ-63）。
- **开源参考**：OWLAPY（Python，MIT，AI 辅助本体构建）验证了该模式；Go 生态无现成等价物，用 Eino 自实现生成循环（这是学习内容，不外包）。
- 产物直接走标准入库路径（version=1），与导入一致。

### 3.4 编辑与扩展（原 REQ-61/63/64/71 + REQ-83）

- **编辑双形态**（沿用 v0.1 §4.1）：P0 JSON 编辑器（校验就地标红 + 三栏只读预览）；P1 图形化（React Flow + RJSF + dagre，spec↔图 adapter，坐标存 localStorage）。
- **校验**（沿用 v0.1 §4.2）：JSON Schema 结构校验 + graph.Build 引用完整性，服务侧执行。
- **fork 扩展（REQ-83，P2）**：本体列表页「复制为新本体」→ 复制全部形态资产（forked_from 记录来源）→ 编辑后作为独立新本体保存；不做"引用继承"（保持简单）。
- **内置示例**（REQ-62）：seed 写入最小 K8s 运维本体（开放问题 O-4 定稿中）。

### 3.5 可视化浏览（REQ-81，开源方案评估结论）

> 依据：《开源本体可视化工具调研_report.md》（2026-09-18，覆盖 WebVOWL/OntoGraf/Ontology Playground/OntView/ontoink/LodLive 等 10+ 方案）。

**需求拆解**：TBox（类层次/对象属性结构浏览）+ ABox（实例间关系查询）两类诉求，开源方案没有单一工具两者都强：

| 层 | 选型 | 许可证 | 理由 | 反转条件 |
| --- | --- | --- | --- | --- |
| **TBox 结构浏览** | **WebVOWL**（自托管 Docker，OWL2VOWL 预转换） | MIT | VOWL 是 W3C 社区视觉标准；类层次/对象属性/数据属性语义丰富；在线版可直接拖文件验证 | 若嫌 Java 预处理重 → **Ontology Playground**（MIT，纯静态零后端，但仅 RDF/XML 输入、深度有限） |
| **ABox 实例关系查询**（SPARQL 型运行方案） | **LodLive** 直连方案 SPARQL 端点 | 开源 | 增量探索式实例关系浏览，天然匹配"查询对象之间关系"；浏览的就是运行中数据 | LodLive 活跃度低（🔴）→ 备选 ontoink widget 或下述复用方案 |
| **ABox 实例关系查询**（memory-graph 型运行方案） | **复用已有 OntologyExplorer 资产**（单文件 HTML，已实现 57 节点关系图/三类语义边/实例详情） | 自有资产 | 已交付可用，数据源对接 spec_json 即可；不重新造轮子 | — |
| **一体化备选** | **ontoink**（embeddable widget 模式） | MIT | 唯一同时覆盖类/属性/个体/SHACL/推理的开源方案（2026-07 活跃） | 若愿意引入 MkDocs/widget 集成成本 |

**集成方式**：本体详情页新增「浏览」入口——①结构视图：WebVOWL iframe（构建平面预生成 OWL2VOWL JSON，缓存按 version 失效）；②关系视图：按运行方案类型路由（SPARQL 型 → LodLive 指向方案端点；memory-graph 型 → OntologyExplorer 加载该本体 spec_json）。**浏览是运行方案的附属视图**（REQ-87 解耦原则的可视化体现）。

## 4. 运行平面设计（v0.2 全新）

### 4.1 运行方案模型（REQ-84/85/86）

```sql
-- runtime-manager/migrations/001_profile.sql
CREATE TABLE runtime_profile (
  id TEXT PRIMARY KEY,                    -- 如 rt_mem_k8s
  name TEXT NOT NULL,
  engine TEXT NOT NULL,                   -- memory_graph | oxigraph | fuseki
  ontology_ids TEXT NOT NULL DEFAULT '[]',-- 加载的本体集合（JSON 数组，仓库 id）
  config TEXT NOT NULL DEFAULT '{}',      -- 细节配置 JSON（端口/推理开关/可写/JVM 参数…）
  port INTEGER,
  status TEXT NOT NULL DEFAULT 'created', -- created|starting|running|stopped|error
  pid TEXT, last_error TEXT,
  created_at DATETIME, updated_at DATETIME
);
```

**状态机**：`created → starting → running ⇄ stopped`；任意态可进 `error`（启动失败/健康检查连续失败）；启停/配置变更经 Manager 编排，状态自动刷新（前端轮询或 SSE）。

### 4.2 运行时类型（engines 适配器）

| engine | 实现 | 加载形态 | 能力 | 学习点 | 交付 |
| --- | --- | --- | --- | --- | --- |
| `oxigraph` | Oxigraph 官方二进制/容器（Rust，MIT/Apache-2.0） | original TTL/OWL（自建本体经 spec_json→TTL 导出） | SPARQL 端点 + 图存储；无 OWL 推理 | RDF 三元组模型、SPARQL、标准部署 | **P1 唯一引擎（O2）** |
| `fuseki` | Apache Jena Fuseki（Java，Apache-2.0，Docker） | original TTL/OWL | SPARQL + **RDFS/OWL 推理**（可配置开启） | 推理语义、企业级本体服务形态 | P1 后期（O6） |
| `memory_graph` | **开源内存图引擎嵌入（不自研，D-O5 v0.4）**：Cayley fork（`NewMemoryGraph` Go 库嵌入）+ 薄语义适配层 | spec_json（经适配层转换装载） | 精确查询（4 工具语义），毫秒级 | 开源引擎集成、语义适配层设计 | **P2 可选（O7，不自研）** |

每个适配器实现统一接口：`Prepare(profile) → Start(profile) → HealthCheck() → Stop()`；数据装载方式按类型（oxigraph：`oxigraph-server` 数据目录 + bulk load；fuseki：创建 dataset + `/data` upload 或 assembler 配置；memory_graph：经语义适配层装载）。

**D-O5 v0.4 要点**：P1 唯一引擎 Oxigraph——onto_*→SPARQL 翻译层随之从原 O6 提前至 O2（本来就要做，只是提前）；自建本体（仅 spec_json 形态）经 O1 的 TTL 导出器获得 original 形态后装载；**TTL 导出器由 Python rdflib sidecar 实现（v0.6：解析与导出同源，Go 侧不再自研 RDF 相关代码）**；memory_graph 不自研（v0.6 定案），P2 若需直接集成开源 Cayley fork，原"spec_json 直载 + 版本自动生效"对照实验随 LG-12 取消而关闭。

### 4.3 Runtime Manager（编排层，自研边界内）

- **生命周期编排**：按 profile.config 启动对应 engine（子进程优先，Docker 可选）；端口分配与冲突检测；健康检查（HTTP 探测，间隔可配）；stdout/stderr 日志采集落盘（页面可看最近日志）。
- **分发**：启动前从构建平面仓库拉取所选本体的对应形态（HTTP 调 `/api/ontologies/{id}/artifacts`）；本体集合变更 → 提示需重启方案生效（v0.2 简化：不支持热加载，热加载进需求池）。
- **降级联动**：主平台挂载的方案停止/崩溃 → 该对话本体查询发 `ONTOLOGY_SERVICE_UNAVAILABLE`，不影响其他方案与普通对话（REQ-70 语义按方案隔离）。

### 4.4 统一 MCP facade（Agent 契约不变）

Manager 内嵌 mcp-go Server（`/mcp`，Streamable HTTP，沿用 Q-14）：`tools/list` 固定返回 4 个 onto_* 工具（签名不变，见 v0.1 §5.2）；`tools/call` 按 `ontology_id` 路由到所属 running 方案——memory_graph 直查内存图；oxigraph/fuseki 将工具语义翻译为 SPARQL（get_concept/get_instance→DESCRIBE/SELECT，list_instances→按 rdf:type 查，neighbors→属性路径查询）。**Agent 侧与主平台无需感知运行时差异**（facade 模式，学习点）。

- 挂载对象变更：对话挂载**运行方案**（conversation 配置存 `runtime_profile_id`），工具入参仍带 `ontology_id` 定位方案内本体（开放问题 O-6，默认按此实现）。
- 即时生效（REQ-73 演进，v0.6 对齐 REQ-87）：P1 全引擎（SPARQL 型）统一**显式重载生效**——本体在构建平面保存新版本后，方案页明确提示需重载，重载后按新版本返回（不静默）；"按版本自动生效"对照语义视 P2 引擎引入情况再评估。

### 4.6 工具链配置层（REQ-74~77，v0.4 新增）

**定位**：在构建/运行两平面之上加一个**流程配置视图**——把 S1~S7 七阶段的工具选择持久化为 pipeline_profile。不引入新引擎：S5 段直接引用 runtime_profile（`stages.s5.tool` 落到 `runtime_profile_id`），一套引擎模型、两个视角（运行方案=运行视图，工具链=流程视图）。

```sql
-- ontology-service/migrations/003_pipeline.sql（P2）
CREATE TABLE pipeline_profile (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  ontology_id TEXT,                       -- 可选：预绑定本体（也可后选）
  runtime_profile_id TEXT,                -- S5 段引用已有运行方案（managed）
  stages TEXT NOT NULL DEFAULT '{}',      -- {"s1":{"tool":"builtin_import","mode":"builtin","params":{}} ... "s7":...}
  checklist TEXT NOT NULL DEFAULT '{}',   -- guided 阶段打卡状态 {stage: {step: done_at}}
  created_at DATETIME, updated_at DATETIME
);
```

**候选工具统一描述（数据驱动，REQ-77）**：

```go
type StageTool struct {
    ID       string   // builtin_import | protege_desktop | webvowl | fuseki | ...
    Stage    string   // s1..s7
    Name     string
    License  string
    Mode     string   // builtin | guided | managed
    Eats     []string // 输入形态: spec_json | original | endpoint
    Gives    []string // 输出形态（交接契约，见七阶段清单 §2）
    Guide    Guide    // guided 模式指引：安装命令/启动命令/数据交接点/入口链接
    Learning string   // 学习要点（配置页卡片展示）
    // P2 编排位：Execute(ctx, profile) error —— 预留不实现（D-O7）
}
```

候选清单存 `tools.json`（随版本维护），增删工具不改核心代码。

**执行模式三态**：builtin 直接可用；guided 由 REST 生成 checklist、前端打卡、状态存 pipeline_profile.checklist；managed 仅 S5（Runtime Manager 现有能力）。**交接契约**（spec_json/original/endpoint）是可插拔的技术基础——工具声明吃什么、吐什么形态即可入列。

**REST（P2）**：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET/POST | `/api/pipelines` | 工具链列表 / 创建（含默认工具链模板） |
| GET/PUT/DELETE | `/api/pipelines/{id}` | 详情 / 修改各阶段选择 / 删除 |

前端：本体详情页新增「工具链」标签页——七阶段纵向步骤条，每阶段候选卡片（名称/许可/模式/形态/学习要点），S5 段内嵌运行方案选择入口（复用运行方案页能力）。

### 4.7 外部独立集成：OpenOntologies 路径（v0.7 新增）

> 依据：《open-ontologies借鉴与引入分析.md》v0.2 §8（2026-09-20 主人拍板：独立集成路径）；主平台对接点（oo-worker :8092、`/api/oo/*` 反代、`OO_MCP_URL`、M8.5 里程碑、验收 15a）以《02_智能体_技术方案设计.md》v0.8 §6.15 为准。

**定位**：open-ontologies（Rust 单二进制，MIT，Oxigraph 0.5 后端，pin 版本）经主平台 **oo-worker 独立托管**（单二进制 + 工作台 + MCP 暴露），与本体两平面**并行双轨、无接口依赖、可整体摘除（P2）**；能力：RDFS/OWL-RL 物化推理、SHACL 校验、不一致检查、变更影响分析（plan/blast radius）、数据装载（CSV/XLSX 等→RDF）、MCP server（39 个 onto_* 工具）。

- **与 D-O5 的关系**：P1 唯一引擎仍为 Oxigraph（不变）；open-ontologies **不作为两平面引擎适配器**（融入式方案搁置），不经 facade/翻译层。
- **数据边界**：该路径本体为 TTL 文件集（worker data-dir 自管），**不进本体仓库 spec_json 体系**；两轨数据 P1 不互通（互通见《03_本体_需求文档.md》REQ-78「P2 TTL 导出互通」）。
- **与七阶段工具链（D-O7）的关系**：仅在 §4.6 `tools.json` 候选清单登记 S3/S5 两条候选（见上），不改变 D-O7 执行模式定义。
- **待验证项**：①open-ontologies `serve` 的 MCP 传输形态（README 中 stdin/stdout 与 streamable HTTP 表述不一致；若为 stdio 由 oo-worker 转 HTTP）；②物化推理与重载成本实测。

## 8. 风险与对策（v0.2 增补）

| 风险 | 对策 |
| --- | --- |
| 多进程编排复杂度（端口冲突/僵尸进程/重复启动） | Manager 单点编排 + pid 记录 + 启动幂等 + 健康检查自动标记 error；本地学习仅回环监听 |
| RDF 型方案的本体更新不同步（编辑后方案里还是旧数据） | memory_graph 版本校验自动生效；RDF 型明确"需重载"提示（不静默）；方案页显示各本体已加载 version |
| SPARQL 工具语义翻译失真（onto_* 语义 ≠ SPARQL 自然映射） | facade 层单测覆盖 4 工具 × 3 引擎的一致性用例；翻译失败返回明确错误 |
| WebVOWL 需 Java 预转换 | 构建平面按 version 缓存 OWL2VOWL JSON；预转换失败降级为"结构浏览暂不可用"，不影响其他功能 |
| LLM 生成质量差/格式漂移 | 结构化输出 + schema 校验 + 最多 3 轮修正循环；始终人工预览确认后入库（不自动保存） |
| 三进程架构学习成本（构建/运行/主平台） | run-dev.sh 一键拉起；接口契约文档化（本文 §5）；里程碑顺序保证先两进程再演进三进程 |
