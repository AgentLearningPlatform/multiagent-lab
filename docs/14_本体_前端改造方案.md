## 1. 现状与问题

### 1.1 现状盘点（2026-09-21）

- 本体模块为单页 `web/src/pages/OntologyPage.tsx`（约 2000 行），信息架构为 **S1~S7 纵向流水线**：S1 本体来源 → S2 编辑 → S3 校验 → S4 可视化 → S5 运行方式 → S6 对外暴露 → S7 对接智能体；左栏本体列表带 S1~S6 完成度圆点（StageDots）。
- 运行方案**以单个本体为中心**：S5 卡片语义是「本体的 S5 段」，列表按"包含当前本体"过滤，空态文案"该本体暂无运行方案"。
- S6（MCP facade 信息）、S7（对话挂载指引 + SPARQL 控制台 + 翻译透视）内嵌在构建流水线尾部。
- API 层 `web/src/api/client.ts` 已**完整覆盖两平面**：`/api/ontologies*`（构建，:8091 反代）、`/api/runtime-profiles*`（运行，:8090 反代），含 start/stop/reload/logs/versions/artifacts/ai-draft/export 等，可全部复用。
- 对话侧 `ChatWindow.tsx` 已按 `runtime_profile_id` 挂载（"本体增强"chip），数据源为运行方案列表，逻辑正确。

### 1.2 与方案（04 v0.8）的三处错位

| # | 现状 | 方案要求（依据） | 判定 |
| --- | --- | --- | --- |
| P1 | 流水线 S1~S4（构建）与 S5~S7（运行/暴露/对接）串成一条线 | 两平面正交：构建平面 UI（/ontologies*）与运行平面 UI（/runtimes*）并列独立（04 §2 架构图） | ❌ 信息架构错位 |
| P2 | 运行方案隶属本体（per-本体 S5 段） | 运行方案是全局一等实体：engine + ontology_ids（多本体集合）+ config；同一本体可被多套方案加载；不同对话挂不同方案（REQ-84/85/86、REQ-87） | ❌ 绑定方向颠倒 |
| P3 | S5~S7 是工具链视图的组成部分 | 工具链 S1~S7 是**两平面之上的第三视角**（流程引导），S5 段只**引用** runtime_profile（`stages.s5 → runtime_profile_id`），不承载运行管理（04 §4.6） | ❌ 视图层级混淆 |

> 结论：主人判断正确。功能覆盖面已基本够，问题出在**信息架构**；本次改造以"重排为主、重写为辅"。

## 2. 改造目标与不动项

**目标 IA（一句话）**：「本体」导航下并列两个一级模块——**本体构建**（管仓库资产：导入/编辑/校验/可视化/导出）与**本体运行**（管运行方案：引擎类型 + 本体集合 + 参数 + 启停/日志/重载），另保留一个降级的**引导流水线**视图（P2）；构建页不出现任何引擎/运行配置，运行页不修改仓库资产，双向只通过"引用"关联（正交 + REQ-87 解耦原则）。

**不动项（本次不改）**：
- 后端 API 契约与双反代（`/api/ontologies*`、`/api/runtime-profiles*`、`/api/ontology-llm/generate`）；
- `client.ts` 现有 API 封装（全部复用，仅增量）；
- 主平台顶部导航六模块结构（本体仍是其一，模块内部再分 Tab）；
- antd 6 + 现有样式体系（`pages.css` 的 `onto-*` 类）；
- `ChatWindow` 的 `runtime_profile_id` 挂载与 `ontology.query / ontology.unavailable` 事件渲染。

## 5. 页面设计

### 5.1 本体构建（BuildPage）

**资产列表**
- 字段：名称、来源徽标（导入/AI/示例/空白）、形态徽标（original TTL/OWL、spec_json）、版本号、构建段完成度 dots（S1~S4）、更新时间。
- 操作：导入、AI 创建、内置示例、空白新建（即原 S1 四入口，收进「新建」按钮组）；编辑、浏览、删除（Popconfirm，文案保留"级联删除 Spec/产物；已启动的运行方案不受影响"——REQ-87）。
- **不出现**：任何引擎、端口、启停配置（正交红线）。

**编辑工作区（选中资产后）**
- Tabs：Spec 编辑（JSON + 保存）｜校验（错误表 + 运行校验按钮）｜版本历史（列表 + 任一版 original 源码查看 = REQ-93 源码视图落点）｜产物清单（artifacts）｜导出 TTL（`/export?format=turtle`，自建本体入 RDF 型方案的前置）。
- 保存成功后的固定提示：**"已保存新版本；运行方案需在其页面显式重载后生效"**（REQ-87，不静默）。
- 可视化：P1 沿用内置 S4Graph；WebVOWL/OntologyExplorer 嵌入为后续增强（见开放问题 3）。

**AI 创建（原 ai-draft 流程）**
- 向导化：领域描述 → 生成草稿 → 校验错误回喂修正 → 预览确认 → 入库（04 §2.1 LLM 创建流）；本轮仅做流程编排，接口不变。

### 5.2 本体运行（RuntimePage）

**方案列表（全局，一等公民）**
- 卡片字段：名称、引擎徽标（`oxigraph` 绿 / `fuseki` 蓝，P1 未交付灰置"即将交付" / `memory_graph` 灰 P2）、**已加载本体 chips（多值）**、状态徽标（created/starting/running/stopped/error 五态映射现有语义）、端口/端点、健康摘要、最近错误（last_error 摘要，Tooltip 全文）。
- 行操作：启动 / 停止 / **重载**（REQ-87 显式重载；暂固定展示，见开放问题 2）/ 编辑配置 / 删除（二次确认，"运行中将先停止再删除"）/ 查看详情。
- 页顶两条全局条：
  - **引擎可用性预检条**：展示引擎就绪状态；预检失败（如 `executable file not found in $PATH`）友好化为"引擎二进制未安装：请在运行环境安装 Oxigraph，或由 Manager 以容器方式拉起"，卡片直接标 error 态并给该指引（对应本次 s5 启动失败场景）。
  - **降级条**：RUNTIME_MGR_URL（:8090）不可达时整页只读 + 说明（沿用现有样式）。
- 空态："暂无运行方案——新建一个方案，选择引擎并勾选要装载的本体"（不再说"该本体暂无运行方案"）。

**新建/编辑向导（Steps 三步，对应 REQ-85）**
1. **选择运行时类型**：P1 仅 Oxigraph 可选；Fuseki 选项展示但 disabled（"随 O6 交付"）；memory_graph 不出现（P2，D-O5）。
2. **勾选本体集合**：多选，数据源 = 构建平面仓库列表；每项带形态提示——SPARQL 型方案装载 original TTL/OWL；仅有 spec_json 形态的自建本体提示"需先在构建页导出 TTL"并引导跳转（04 §2.1 分发流）。
3. **细节参数**：名称、监听端口（默认自动分配）、SPARQL 端点可写开关、推理开关（P1 灰置，随 Fuseki）；保存后固定提示**"配置变更需重启方案后生效"**。

**方案详情（Drawer，按 Tab 组织）**
- 概览：状态时间线（created→starting→running⇄stopped/error）、端口/端点、配置摘要、"编辑后需重启"提示。
- 日志：`/logs?tail=200` 拉取 + 刷新（原 S5 日志逻辑迁移）。
- facade 与工具（原 S6 迁移）：统一 MCP facade 端点（随**本方案**暴露）、onto_* 4 工具表。
- 查询与挂载（原 S7 迁移）：对话挂载指引（全局口径："在对话输入框「本体增强」chip 中选择 running 方案"，不再限定"本本体"）、SPARQL 控制台（方案 running 时可用，非 running 提示 409）、翻译透视表（Trace）。
- 挂载对话：展示当前挂载本方案的对话（只读，若后端暂无该查询则此 Tab 先隐藏，见开放问题 5）。

### 5.3 引导流水线（GuidePage，P2 可暂隐）

- 保留现有 S1~S4 引导内容为"流程视角"（工具选择/指引/打卡，04 §4.6、D-O7）。
- **S5 改为引用卡**：显示关联的运行方案名 + 状态 + 「前往本体运行」跳转；不再内嵌方案管理操作（`stages.s5 → runtime_profile_id` 的引用语义）。
- **S6/S7 改为只读信息卡**：facade 状态、挂载指引，操作入口指向方案详情。
- 本视图不进入默认 Tab 顺序（排在最后或先隐藏），避免再次与两平面混淆。

## 6. 数据与状态约定

- API：全部复用 `client.ts` 现有方法；增量仅两处——①方案详情若需展示挂载对话，待后端补查询接口；②引擎预检建议 Manager `/healthz` 增补 engines 段（开放问题 1），未提供前前端按 last_error 关键词映射友好文案。
