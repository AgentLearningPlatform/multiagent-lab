## 1. 方案摘要

- **推荐路线**：前端工程 monorepo 化，一套 React 代码多端复用——**Web/PWA 先行（T0~T1）→ 桌面端 Tauri 2（T1，Go 后端以 sidecar 随壳分发，实现"一键启动整个平台"）→ 移动端 Android 套壳（T2）→ iOS 与推送（T3）**。
- **关键决策**：
  1. 后端零改动多端化：Go 单二进制 + REST/SSE 天然支持多客户端，不引入 BFF/网关；
  2. 桌面端选 **Tauri 2** 而非 Electron：体积小、复用系统 WebView，且 sidecar 机制可把 Go 后端打进同一个安装包（Electron 也可做但包体与内存成本高）；
  3. 移动端先走 **WebView 复用路线（Tauri mobile / Capacitor）**而非 React Native：保住已拍板的全蚂蚁生态（AntD 5 / Pro Components / Ant Design X 均为 DOM 组件，RN 不可用），UI 只做移动适配不重写；
  4. 认证与"服务器地址可配置"是所有多端形态的**前置改造**（当前客户端隐含 localhost 假设）。
- **预期收益**：同一业务代码支撑 Windows/macOS/Linux 桌面端与 Android/iOS/PWA，新增端边际成本递减；桌面端形成"安装即用"的本地平台形态。
- **最大风险**：移动端 WebView 内 SSE 长连接在后台/弱网下的稳定性（不可断点续传，需重连与状态补偿）；iOS 签名分发对个人学习场景不友好（PWA 可规避）。
- **评审阻塞项**：无 P0 阻塞。开放问题 O-2（移动端管理功能的裁剪边界）建议在 T1 结束前确认，不阻塞本方案评审。

## 2. 背景与目标

| 项 | 内容 |
| --- | --- |
| 业务背景 | eino-multiagent-lab 定位为**本地学习用多智能体平台**（01 PRD：Go 后端 + React SPA + SQLite + OpenAI 兼容模型协议，预置 DeepSeek）。当前唯一客户端是桌面浏览器访问 `localhost:8080` 的 Web SPA。 |

## 6. 方案选型与决策

### 6.1 关键决策一：桌面端壳 —— Tauri 2（推荐）vs Electron

| 评估标准 | 权重 | Tauri 2 | Electron | 说明 |
| --- | ---: | ---: | ---: | --- |
| 前端复用度 | 20 | 5 | 5 | 两者都直接加载现有 Vite 构建产物 |
| 包体/内存 | 15 | 5 | 2 | Tauri 复用系统 WebView（Windows=WebView2、macOS/iOS=WKWebView、Linux=webkit2gtk，E3）；Electron 自带 Chromium，包体几十 MB 起且常驻内存高 |
| Go 后端一体化分发 | 20 | 5 | 3 | Tauri sidecar 机制原生支持管理外部二进制（E8）；Electron 需自行处理进程拉起/打包（可行但工程量多） |
| 生态成熟度 | 15 | 3 | 5 | Electron 生态最成熟、踩坑资料最多；Tauri 2 已稳定但移动侧生态较新 |
| 移动端路线一致性 | 15 | 5 | 1 | Tauri 2 桌面/移动同框架，一套壳工程经验可迁移（E3）；Electron 无移动端 |
| 团队上手成本 | 15 | 3 | 4 | Electron 纯 JS；Tauri 需要少量 Rust（本项目壳层预计 < 300 行 Rust） |
| **加权合计** | 100 | **4.5** | **3.2** | — |

- **推荐**：Tauri 2。决定性因素是"桌面+移动同框架"与 sidecar 一体化分发，直接服务 SC-X1 与 R-X3。
- **放弃 Electron 的理由**：无移动端路线、包体/内存劣势；无决定性优势项。
- **反转条件**：若 T1 PoC 中 Tauri sidecar 与 updater 出现硬伤（无法满足 SC-X1），或团队不愿引入 Rust 工具链，切回 Electron（前端代码不受影响，仅壳层重写）。
- 置信度：medium-high。

### 6.2 关键决策二：移动端路线 —— WebView 复用（推荐）vs React Native/Expo vs Flutter

| 评估标准 | 权重 | Tauri mobile / Capacitor（WebView 复用） | React Native + Expo | Flutter |
| --- | ---: | ---: | ---: | ---: |
| 蚂蚁生态 UI 复用 | 25 | 5（AntD/X 原样运行于 WebView） | 1（DOM 组件库不可用，E6） | 1（同左，且跨栈） |
| 移动端体验上限 | 20 | 3（WebView 渲染，列表/动画弱于原生；对话流场景够用） | 5（原生渲染） | 5 |
| 交付速度/成本 | 20 | 5（复用 ≥90% 前端代码，仅做响应式与移动导航） | 2（对话区、管理页、SSE 流全部重写，等于第二个前端） | 2 |
| 生态/长期维护 | 15 | 4（Tauri 2.11 移动支持成熟 E3；Capacitor 8.x 活跃 E4） | 5（Expo/RN 生态最活跃 E5） | 4 |
| 与现有 Go/React 团队技能匹配 | 10 | 4 | 3 | 2 |
| iOS 后台/推送等系统能力 | 10 | 3（插件覆盖常用能力，推送需接 FCM/APNs） | 5 | 4 |
| **加权合计** | 100 | **4.25** | **3.05** | **2.75** |

- **推荐**：移动端走 **WebView 复用**（T2 用 Tauri mobile 与桌面同构；若 Tauri 移动插件在某项系统能力上缺失，单点改用 Capacitor 补位——两者同为 WebView 方案，前端代码 100% 共享）。Flutter 直接排除（与 React 栈割裂，双栈维护成本最高）。
- **放弃 RN/Expo 首选的理由**：唯一致命点是 AntD 5 / Pro Components / Ant Design X 均不可用（E6），等于放弃已拍板的前端选型重写第二套 UI；对话流式渲染（x-markdown）也需另寻 RN 方案。Expo 生态再活跃也无法弥补"学习平台核心界面是对话区"这一事实。
- **反转条件**：①移动端对话体验经 T2 实测明显劣化（滚动/长列表/键盘遮挡不可接受）且调优无果；②产品重心从"学习平台"转向"移动优先的多端产品"，此时再评估 Expo 重写对话区（保留 x-sdk 数据层复用可能，E6 备注）。置信度：medium。

### 6.3 决策汇总表

| 决策点 | 推荐 | 放弃方案 | 理由 | 反转条件 |
| --- | --- | --- | --- | --- |
| D-X1 桌面壳 | Tauri 2 | Electron | sidecar 一体化 + 桌面/移动同框架 | sidecar/updater PoC 硬伤 |
| D-X2 移动端 | WebView 复用（Tauri mobile，必要时 Capacitor 补位） | Expo/RN、Flutter | 保蚂蚁生态 UI，代码复用 ≥90% | 移动对话体验不可接受 |
| D-X3 中间形态 | PWA 先行（T0~T1 内交付） | 直接做原生壳 | 零打包成本即可获得"手机可用"，且是移动适配的试验场 | 无 |
| D-X4 后端 | 零改动 + 增量 API（auth/version/health） | 为移动端新建 BFF/网关 | 本地学习平台无多端差异化数据需求 | 出现服务端聚合类新需求 |
| D-X5 认证 | 简单 JWT/API Token（SQLite users 表） | OAuth2/OIDC 完整体系 | 单机/局域网学习场景够用，避免过度设计 | 未来开放多人使用 |

## 7. 目标架构

### 7.1 Context view（信任边界）

```
                    ┌──────────────────────────── 信任边界（同一部署单元）────────────────────────────┐
                    │                                                                                │
  桌面客户端         │   Go 后端 :8080（单二进制，REST + SSE）        外部依赖                          │
 ┌──────────────┐   │  ┌──────────────────────────────────────┐   ┌────────────────────┐           │
 │ Tauri 2 壳    │   │  │ Agent 编排(Eino ADK) / 知识库 / 技能  │   │ 模型 API(DeepSeek  │           │
 │  ├ Web UI ───┼───┼─▶│ 模型连接 / 本体 facade 代理(:8090/:8091)│   │ OpenAI 兼容端点)   │           │
 │  └ Go sidecar┼──▶│  │ SQLite(主库)  Qdrant(可选 :6333)      │   └────────────────────┘           │
 │    (内嵌模式) │   │  │ Docker P1 沙箱 / K8s P2（可选）        │   本体两平面(独立部署,可选)         │
 └──────────────┘   │  └──────────────────────────────────────┘                                    │                    │
  手机 App / PWA    │                                                                                │
 ┌──────────────┐   │                                                                                │
 │ WebView 壳 /  │───┼─▶ 同一 :8080（局域网 IP 或远程域名 + HTTPS + Token）                            │
 │ 浏览器        │   │                                                                                │
 └──────────────┘   └────────────────────────────────────────────────────────────────────────────────┘
```

- 三种客户端形态消费**同一后端**；桌面端可选**内嵌模式**（sidecar 同机）或**远程模式**（连接局域网/远程后端），移动端只有远程模式。

### 7.2 Component view（前端 monorepo）

```
eino-multiagent-lab/
├─ backend/                       # Go 后端（现有，零改动 + 增量 API）
├─ web/                           # 现有前端目录（02 §4.3）→ 升级为 pnpm workspace
│  ├─ packages/
│  │  ├─ ui/                      # 蚂蚁生态组件与页面（现 SPA 的页面/组件平移至此）
│  │  ├─ api/                     # API client（REST 封装 + SSE 客户端，含 baseURL/Token 注入）
│  │  ├─ core/                    # 领域状态（会话/消息/配置的 store、SSE 重连策略）
│  │  └─ platform/                # 端能力桥接接口（notification/tray/clipboard 等，按端注入实现）
│  └─ apps/
│     ├─ web/                     # 纯 Web + PWA 入口（现 SPA + manifest/service worker）
│     ├─ desktop/                 # Tauri 2 桌面壳（src-tauri/ + sidecar 配置 + updater）
│     └─ mobile/                  # Tauri mobile / Capacitor 移动壳（移动导航 + 适配层）
```

- 分层铁律：`ui` 不直接 fetch；`api` 不含业务；`core` 不碰 DOM 之外的平台 API；端差异只出现在 `apps/*` 与 `platform` 实现。

### 7.3 Runtime flow（SSE 对话多端一致）

```
客户端(SSE client in packages/api, x-sdk 适配)
  1  POST /api/auth/token ──▶ JWT（内存持有；移动端另存 Keychain/Keystore，P2）
  2  POST /api/agents/:id/chat (SSE) ──▶ 事件帧(ThoughtChain 步骤/消息增量/完成)
  3  断流检测(heartbeat 超时 3s) ──▶ 指数退避重连(≤3 次)
  4  重连后 GET /sessions/:sid 补拉状态 ──▶ UI 对账(去重 by message_id)
```

- 现有 SSE 事件协议不变（02 §6 SSE 帧定义）；重连补偿只依赖已有查询接口，后端不新增续传机制。

### 7.4 Data view

- 主数据仍归后端 SQLite；客户端仅持有：服务器地址、Token（内存/安全存储）、UI 偏好（localStorage / Tauri store）。
- 不引入客户端数据库；离线只缓存只读列表（P2，可选）。

### 7.5 Failure view

| 故障 | 表现 | 降级 |
| --- | --- | --- |
| sidecar 拉起失败（端口占用/依赖缺失） | 桌面端启动报错页 | 提示改用远程模式连接已运行后端 |
| SSE 断流 | 对话停止 | 自动重连 + 状态补拉（7.3）；3 次失败转手动重试 |
| Token 过期 | 401 | 静默刷新一次，失败回登录/重新配钥页 |
| 移动端后台被杀 | 回前台白屏 | 冷启动 → 恢复最后会话列表（R-X7） |
| 远程后端不可达 | 连接诊断页 | 按 DNS/端口/认证/版本四步诊断提示（R-X1） |

## 9. API、事件与数据契约（增量）

| 契约 | 类型 | 请求/字段 | 响应/状态 | 幂等/重试 | 兼容性 |
| --- | --- | --- | --- | --- | --- |
| `/api/auth/token` | API | `{username, api_key}` | `{token, expires_in}`；401 认证失败 | 可重试 | 新增，不影响既有本地无认证用法（本地模式由桌面壳自动获取） |
| `/api/version` | API | GET | `{version, min_client_version}` | 可重试 | 新增；客户端据此做兼容性诊断（R-X1） |

| 客户端配置 | 本地 | `server_url`、`token`、UI 偏好 | — | — | 各端各自存储，无服务端 schema 变更 |

## 10. 容量、性能与压测说明

本平台为**本地学习定位**（E2），不适用互联网式容量规划；仅约束客户端相关性能点：

| 项 | 公式/来源 | 估算值 | 置信度 | 验证方式 |
| --- | --- | --- | --- | --- |
| SSE 并发流 | 单用户学习场景，主瓶颈是模型端点而非后端 | 峰值 2~5 路（含对比模式 N 路） | high（由产品形态决定） | 对比模式实测（对齐 01 验收 12a） |
| 桌面包体积 | Tauri 壳(~5-10MB) + Go 二进制(~20-30MB，含依赖) | ≤ 60MB（R-X8） | medium | 打包度量（TODO：T1 实测） |
| 移动 WebView 内存 | 经验值，WebView 进程常驻 150~300MB | 可接受（学习场景） | low | 真机 Profile（T2） |
| 重连时延 | 心跳 3s 超时 + 退避(0.5/1/2s) | ≤ 3s 内发起重连（R-X6） | high | 弱网注入 |

## 11. 安全、隐私与合规

| 风险点 | 控制措施 | 验证方式 |
| --- | --- | --- |
| 后端暴露局域网后的未授权访问 | R-X2 Token 认证默认开启（远程模式强制）；本地 loopback 模式豁免 | 未带 Token 请求 401 实测 |
| 明文传输（局域网 HTTP） | T2 起提供 HTTPS 指引：反代（Caddy/自签）或内网证书；App 端允许用户显式信任自签证书（Android network config / iOS 例外声明，P2） | 抓包验证 |
| API Key 落地客户端 | 移动端仅存 Token（Keychain/Keystore，P2），不落 API Key——模型 Key 始终只在后端 | 移动端存储审计 |
| 桌面 sidecar 本地端口被其他进程占用/冒用 | 动态端口 + 启动时校验 `/api/version` 指纹；仅绑定 127.0.0.1（内嵌模式） | 端口冲突场景测试 |
| 自动更新供应链 | updater 签名校验（Tauri 官方机制） | 升级演练（R-X10） |
