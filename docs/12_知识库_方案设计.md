## 3. 总体设计

### 3.1 管道视图

```
索引管道（异步，状态机）                    检索管道（对话内同步）
┌────────────┐   ┌──────────┐   ┌─────────────────┐
│ 文档入库    │→ │ 切分器    │→│ Embedding(模型连接)│
│ txt/md/粘贴 │   │ 块/重叠   │  │ OpenAI 兼容       │
└────────────┘   └────┬─────┘   └────────┬────────┘
                      ↓                   ↓
              chunk 表(正文+状态)     VectorStore 接口(可插拔)
                      ↓            ┌────┴─────┐
                索引状态回写        │ Qdrant(P1)│  │ SQLite fallback│
              (待处理/处理中/就绪/失败) └──────────┘  └───────┘

对话提问(选了知识库) → retrieve(query, topK, threshold) → 片段+得分
   → 拼接上下文 → SSE `retrieval` 事件(来源+摘要，REQ-17) → Agent 生成
```

### 3.2 可插拔 Store 抽象（自 02 §6.9 原样承接，接口不变）

```go
type VectorStore interface { // 两种实现
    Upsert(ctx, kbID string, chunks []Chunk) error
    Search(ctx, kbID string, vec []float32, topK int, minScore float64) ([]Hit, error)
    DeleteByDoc(ctx, kbID, docID string) error
}
// QdrantStore（P1 首选）：eino-ext 现成 indexer/retriever 适配优先（M6 首日核对可用组件清单后定稿对接方式），
//   无适配则直连 Qdrant REST（collection=kb_{id}，cosine，point id=chunk id）
// SQLiteStore（fallback）：沿用 v0.5 SQLiteRetriever（余弦 TopK），保留为无外部依赖对照（不删）
```

- 选择逻辑：配置 `KB_STORE=qdrant|sqlite`；Qdrant 启动探测不可达 → 自动落 SQLite fallback 并在索引状态提示（降级语义，不阻断建库；探测为部署层逻辑，不属接口成员）。
- **不编造组件**（02 §6.9 既有约定，转为 KB-O1）：eino-ext 具体 indexer/retriever 适配是否齐备在 M6 实现首日核对官方仓库后定稿；均不适用则 Qdrant 直连 REST，仍属开源优先范畴。

### 3.3 数据模型（自 02 移入）

三表沿用 02 v0.5 结构（`kb` / `doc` / `chunk` + 状态字段）；`knowledge_chunk` 增列 `store_backend TEXT DEFAULT 'sqlite'`、`vector_ref TEXT`：

| 表 | 关键列 | 说明 |
| --- | --- | --- |
| `kb` | id, name, brief, top_k, threshold, created_at | 库级检索参数（REQ-57） |
| `doc` | id, kb_id, name, status, chunk_count, dim, updated_at | 文档单位（REQ-51/54）；status：待处理/处理中/就绪/失败 |
| `chunk` | id, doc_id, kb_id, content, status, store_backend, vector_ref(BLOB 或 Qdrant point id) | 正文恒存 SQLite；Qdrant 路径向量存 Qdrant，fallback 路径 BLOB 直存 |

- 对话关联：`conversation.kb_id`（01 REQ-19a）留 02 平台库；知识库侧不感知会话。

### 3.4 API 与事件契约

| 契约 | 内容 | 兼容性 |
| --- | --- | --- |
| REST | `/api/kbs` CRUD；`/api/kbs/{id}/docs`（POST 粘贴文本/上传 txt md，DELETE 级联）；`POST /api/kb/{id}/search-preview` 试运行直接返回命中（02 §6.9 原路径承接，REQ-57） | 自 02 §5 承接，不变 |

| 部署 | Qdrant :6333 可选容器（02 §4.1 已列入）；SQLite 路径零新增依赖 | 不变 |

### 5.3 WeKnora 0.8.0 深度评估（主人点名对象）

**能力对比（WeKnora 0.8.0 vs 本项目知识库当前范围）：**

| 维度 | WeKnora 0.8.0 | 本项目知识库（11 需求） | 差距性质 |
| --- | --- | --- | --- |
| 文档接入 | 20+ 格式 + OCR/表格/VLM/ASR + 多平台同步 | 粘贴文本 + txt/md | **WeKnora 强**，但超出本项目 Non-Goals（11 KB-2 进阶池） |
| 检索 | 混合检索 + RRF + Rerank + 改写 + 意图识别 | 向量 TopK + 阈值 | WeKnora 强，同属进阶池 |
| 知识组织 | Wiki / GraphRAG / FAQ / 预生成问题 | 无 | WeKnora 强，进阶池 |
| Agent 能力 | 自带 ReAct Agent + Skill 沙箱 + 长期记忆 | 不适用（本项目 Agent 编排属主平台核心自研区，Eino ADK） | **职责重叠**：引入即第二套 Agent 体系 |
| 集成形态 | 完整成品：整体部署经 API/MCP 使用（自带 MCP Server） | 平台内模块：进程内组件 + 共享库表 | 形态不同层 |
| 技术栈 | Go 后端 ✓ / **Vue 3 前端**（与已拍板蚂蚁生态 React 冲突）✗ / Python 解析服务（多一个运行时）✗ | Go + React（蚂蚁生态） | 部分冲突 |
| 资源 | 标准：PostgreSQL+pgvector+Qdrant+（可选 Neo4j）多容器；**Lite：单二进制 SQLite+FTS5+sqlite-vec 零依赖** | SQLite 单机 + Qdrant 可选容器 | 相当（Lite 模式与本项目 fallback 思路同构） |
| 许可与活跃 | MIT、~24.4k stars、微信 AI 团队维护（E1） | Qdrant Apache-2.0；eino-ext 云原生社区 | 均可商用 |

**逐条回答"是否有比 WeKnora 0.8.0 更合适的方案"：**

1. **若问题是"知识库功能谁更强"**：WeKnora 0.8.0 在开源 RAG 平台里属第一梯队（功能面全、MIT、微信 AI 背书、活跃），RAGFlow 0.27 的深文档理解/知识编译与之互有胜负，Dify 偏应用平台。**没有明显更强的成品平台**。
2. **若问题是"对 eino-multiagent-lab 哪个更合适"**（真实语境，E7）：**维持现状方案（eino-ext + Qdrant + SQLite fallback）更合适**，WeKnora 不是替代项：
   - **学习目标冲突**（LG-11）：本项目知识库的存在意义是学 RAG 闭环搭建；引入成品即放弃该学习目标——相当于用现成答案替代练习题。
   - **架构职责重叠**：WeKnora 自带会话、Agent、编排、沙箱——与本平台核心（Eino ADK 多智能体编排）整体重复；引入等于"平台里再装一个平台"。
   - **集成成本不对称**：其价值集中在文档解析与进阶检索（OCR/GraphRAG/混合检索），全部在 11 KB-2 需求池（本项目明确不做）；为池内需求引入整套外部系统不划算。
   - **技术栈摩擦**：Vue 3 前端无法融入已拍板的 React/蚂蚁生态界面体系（06 v0.7）；Python docreader 增加运行时；标准部署多容器超单机学习尺度（Lite 模式虽轻但那样只用它的 SQLite 检索，价值更低）。
   - **集成口径**：WeKnora 是"另一个 OpenOntologies 式外部服务"的正确候选——经其 MCP Server 独立接入、Agent 挂载工具，与平台内组件级知识库**并行不替代**（11 KB-3，P2 备选）。
3. **组件层是否换血**：不换。Qdrant（Apache-2.0、单容器、Eino 生态适配在核对清单 KB-O1）与 WeKnora 内部可插拔向量库选项（E4）重叠，能力满足 TopK 检索；sqlite-vec 可作为 SQLiteStore 的演进选项（当前余弦全扫在学习尺度下够用，不引入 C 扩展依赖）。

### 5.4 选型决策（承接 01 Q-18 / KB-1，收敛为正式决策）

| 决策点 | 结论 | 放弃方案 | 理由 | 反转条件 | 置信度 |
| --- | --- | --- | --- | --- | --- |
| D-KB1 知识库实现形态 | **平台内组件级**：eino-ext 适配优先 + Qdrant（P1），SQLiteRetriever fallback（学习对照） | 平台级成品（WeKnora/RAGFlow/Dify 整体引入） | §5.3：学习目标、架构重叠、进阶池边界、技术栈一致性 | 董奎将知识库定位改为独立产品/需要完整企业知识库能力 | high |
| D-KB2 进阶能力获取路径 | 进阶能力（OCR/GraphRAG 等）**不自研不引入**，留 11 KB-2 池；触发时**优先评估 KB-3 独立服务集成**（WeKnora MCP / RAGFlow API，对标 OO 双轨模式） | 自研进阶 RAG；替换主方案 | 触发概率低（学习平台）；双轨可整体摘除、不污染主平台 | 进阶需求成为 P1 且自研成本评估 > 集成成本 | medium |
| D-KB3 向量库 | Qdrant 维持首选（单容器 REST/gRPC，cosine） | pgvector/Milvus/Weaviate | Eino 生态适配路径最短（KB-O1 核对后定稿）；单机学习尺度够用 | eino-ext 适配均不可用且直连成本高 → 评估 pgvector（与主库合并） | high（待 KB-O1 定稿） |

**结论一句话**：当前方案（eino-ext + Qdrant + SQLite fallback）就是针对本项目语境"比 WeKnora 0.8.0 更合适"的方案——因为合适性由学习目标与架构边界决定，而非功能面；WeKnora 0.8.0 作为 P2 独立集成候选归档（11 KB-3），其 Lite 模式（SQLite+FTS5+sqlite-vec 零依赖）与本项目 fallback 思路同构，反向印证了轻量路线的合理性。
