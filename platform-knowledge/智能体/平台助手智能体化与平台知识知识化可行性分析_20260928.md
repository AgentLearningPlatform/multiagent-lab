## 0 开篇结论

**两问都可行，且互为闭环：分析②是分析①的知识底座，分析①是分析②的消费出口。** 建议合并为一个需求分两期：P1 做平台知识 KB 化 + 平台助手对话化（含只读工具面），P2 做配置写操作（diff 确认两段式）+ KG 化实验。

- **分析①（平台助手进智能体界面）**：**可行，底座现成度高**。后端对话循环、工具装配、多轮会话、前端 ChatWindow 全部有既有实现可复用；主要工作不在技术难度，而在三件事——①修订 REQ-166「不占用户 Agent 列表」约束（需求变更，需开发者拍板）；②给平台助手配一套**分级工具面**（只读开放 / 写操作白名单 + diff 确认）；③平台知识注入采用三级方案（L1 提示词索引 / L2 docRead 工具 / L3 KB 检索工具，L3 依赖分析②先行或同期）。
- **分析②（平台知识 → KB / KG）**：**KB 化强烈可行且成本低（管线现成，预计 1~2 天量级）；KG 化可行但价值需诚实评估，建议后置为 P2 实验**。42 份 md / 约 715K 的文档型知识，向量检索（KB 路线）可覆盖绝大部分消费场景；KG 化的增量价值在「实体关系查询与多跳」，但 LLM 抽取质量与同步维护成本高，Go 生态无原生 GraphRAG 管线（[25 号调研](../知识库/25_Agent知识库与知识图谱构建接入方案.md) §4 结论），对本项目文档型知识收益/成本比不高——与伴生本体（REQ-170）"薄本体"哲学一致：不为图谱而图谱。

## 3 分析①：平台助手进智能体界面（内置智能体化）

### 3.1 可行性结论

**可行。** 技术上无阻塞项，底座复用度高（对话循环/工具装配/SSE/前端组件全部现成）；真正的约束是**需求层面的**：REQ-166 定下的「不占用户 Agent 列表、不可删除」与本次方向相反，属于**需求变更，需开发者拍板修订**（立项时同步修订 01/18 对应表述）。

### 3.2 进界面方案：两个候选

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 前端固定卡片 + 专用对话端点（推荐）** | 智能体列表前端渲染一枚固定"内置"卡片（不可编辑/删除，带内置徽标）；后端新增 `/api/assistant/chat` SSE 端点，内部用 `newChatModelAgent` 组装平台助手专属 agent + 工具面；会话独立存储（复用 chat 会话表，agent 标识区分） | agent 表零污染（内置与用户资产物理隔离，REQ-166 精神部分保留）；配置仍走 assistant_config 单行表；删除/编辑入口天然不存在 | 前后端各加一条"内置特例"分支；列表排序/筛选逻辑需感知内置项 |
| B. agent 表内置行 | agent 表插入固定 id 行（如 `builtin-assistant`），is_builtin 字段标记 | 列表/对话链路完全复用，无特例分支 | agent 表被系统数据污染；CRUD 处需处处防用户改/删内置行；配置两处（assistant_config + agent 行）易漂移；与 REQ-166 精神冲突最大 |

**推荐 A**：侵入面最小、与既有「inprocess 不落表」架构连续性最好，且天然规避 B 的所有防误删逻辑。

### 3.3 工具面设计：分级权限（"能对系统配置做出修改"的安全边界）

这是本分析最重要的设计点。平台助手拿到工具后，能力边界=工具边界。建议三级：

**L0 只读（默认全开，低风险）：**
- `doc_read`：复用 docRead 白名单逻辑包装为工具（读 platform-knowledge/ 与 docs/）——平台知识的主要供给通道；
- `list_model_connections` / `list_agents` / `list_kb` / `get_assistant_config`：列表与当前配置查询——"答疑+配置辅助"角色的信息底座；
- `search_platform_kb`：KB 检索工具（依赖分析②，见 §4）。

**L1 写操作白名单（高风险配置，diff 确认两段式）：**
- 首批白名单建议收窄为两类低危高频项：**assistant_config 自身修改**（提示词微调/模型/温度）与 **KB 文档导入/重建索引**；
- 交互模式**复用 REQ-167 已验证的 diff 预览确认**：助手输出"拟修改 JSON diff"→ 前端确认 → 才真正调用 PUT/POST。即**助手只产出提案，执行权在用户确认动作**；
- 模型连接增删改、智能体配置改等高危写**不进首批白名单**（改错模型连接影响全平台推理），留待运行观察后评估。

**L2 明确不做：** 直接执行无确认的写操作；删除类操作（KB 文档删除也不进白名单——防误删 715K 资产）。

> 两段式（提案→确认）是本方案的安全基石：LLM 幻觉或误操作被前端确认环节拦住；这与平台已有 REQ-167 交互心智一致，无新交互范式成本。

### 3.4 平台知识注入：三级方案（与 §4 联动）

| 级别 | 机制 | 成本 | 效果 |
| --- | --- | --- | --- |
| L1 提示词 | assistantDefaultPrompt 追加 platform-knowledge/ 目录树索引（42 文件名+一句话定位，约 1.5K tokens） | 极低（改一个常量） | 助手"知道有什么"，可引导用户、精准调用 doc_read |
| L2 工具 | doc_read 工具按需读全文（白名单已有） | 低（工具包装） | 按需检索，不占上下文 |
| L3 检索 | search_platform_kb 工具（KB 向量检索 topK 注入） | 中（依赖分析② P1） | 跨文档语义查找，715K 全文无法靠 L2 逐个读 |

三级叠加后，"具备平台知识"的语义完整：L1 知边界、L2 能精读、L3 能泛搜。

### 3.5 工作量与风险

**工作量粗估（P1 口径，不含分析②的 KB 化）：**
- 后端：assistant chat SSE 端点 + agent 组装 + L0 工具包装（doc_read/列表/get_config）+ 会话存储 —— 约 2~3 天；
- 前端：智能体列表内置卡片 + 对话页复用 ChatWindow + diff 确认组件复用 —— 约 2 天；
- L1 写工具（assistant_config 修改 + diff 两段式）—— 约 1 天。

**风险：**
1. **提示词注入面扩大**：平台知识文档内容进入助手上下文，若文档被写入诱导性内容，助手可能被操纵（L1 写操作有确认环节兜底，风险可控；长期可加"工具提案内容不直接执行"的注入检测）；
2. **内置卡片与用户资产的交互细节**（搜索/筛选/排序是否混排）需产品口径拍板；
3. REQ-166 修订涉及 01/18 两处文档表述同步（git 纪律内处理，非技术风险）。

## 4 分析②：平台知识 → 知识库 / 知识图谱

### 4.1 两条路线对比

| 维度 | 路线 A：KB（向量知识库） | 路线 B：KG（知识图谱） |
| --- | --- | --- |
| 底座 | **全现成**：KB.Import + embedder/qdrant/split 管线已交付，只差"导入任务+搜索入口" | 部分现成：GraphragIngest 在；但 Go 无原生 GraphRAG 构建管线（25 号 §4），抽取质量依赖 LLM |
| 核心工作 | ①同步任务：platform-knowledge/ 目录扫描→切 chunk→Import（增量：mtime/git commit 比对）；②建"平台知识"专用 KB 或 kb 维度标记；③搜索入口（previewKBSearch 直接可用） | ①LLM 抽取实体/关系（每文档一次 LLM 全量调用，715K 约 42 次起）；②graph=pk 命名图写入（仿 companion 模式）；③SPARQL/GraphRAG 检索入口；④同步维护（文档改→图重建） |
| 成本 | **低（1~2 天量级）**，且与 REQ-171 P2⑤「KB Data Pipeline 增强」直接衔接 | **高（S-M 起步，抽取+同步+检索三段）** |
| 价值 | 语义检索覆盖文档型知识 80%+ 消费场景（"怎么配置模型连接""伴生本体是什么"类问题） | 增量价值=实体关系多跳（"哪些文档提到 Oxigraph 且与 REQ-151 相关"）——对**叙述型文档**收益有限；对**结构化关系**（REQ 依赖/模块归属）有价值但这类关系 docs/18 注册表已是结构化事实源 |
| 风险 | 低：独立 KB 不动现有管线 | 抽取质量不稳（文档型知识实体边界模糊）；同步维护成本长期存在；与 D-O15"去重运行时依赖"需对齐（不引 Python 服务前提下只有自研薄层一条路） |

### 4.2 结论与建议

- **路线 A（KB）先行，P1 落地**：42 md 批量导入 + 增量同步 + 检索工具化（供 §3.4 L3 与智能体通用消费）。诚实评估：这一步即可让"平台知识检索"达到可用水位。
- **路线 B（KG）后置为 P2 实验**：不预承诺。触发条件建议——P1 上线后若助手对"跨文档关系类"问题检索命中率不足，再启动；届时优先评估**非 LLM 抽取的轻量路径**（如 docs/18 注册表、03/04 需求文档这类天然结构化源直转，而非全量 md LLM 抽取），这更符合动态薄本体子课题"薄"的方法论。
- **归一**：两路线共享同一同步触发器（文档变更→更新），P1 只接 KB 下游，P2 若启动再挂 KG 下游——管线设计时留出分叉即可，零返工成本。

### 4.3 与既有排期的衔接

- **REQ-171 P2⑤「KB Data Pipeline 增强」**：本分析 P1 的导入/同步任务即其具体化落点，立项时建议直接挂靠（P2 批次已有整体排期：4ac5d92 拍板方案 1，M-O14 段），避免新开平行工程；
- **REQ-159+（25 号调研）**：业界选型依据已在，本分析不重复选型，只做"平台知识这一具体资产"的落点决策；
- **11 号知识库需求文档 KB-3**：「Agent 挂载 KB」已列为 P2 备选（WeKnora/RAGFlow 经 MCP）——本分析给出的内联"KB 检索工具"是同一需求的更轻实现（不引外部服务），两者不冲突，外部 MCP 路线仍可作为远期备选。
