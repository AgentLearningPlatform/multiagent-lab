## 一、定位：报告路线 × 项目语境的映射

报告的核心命题是**记忆系统视角的动态本体**：智能体长期多会话运行中存在"隐式召回失败"（当前提问与早期陈述无词汇重叠时 dense 检索漏召，Recall@10 从 0.61 跌至 0.28），运行时从对话数据自动归纳一张轻量本体图可使检索在概念层运作（Recall@10 0.706、成本较长上下文降 81%）。报告给出三档路线，其**轻量档**（固定种子 schema + 运行时仅实例填充，1-2 人 / 4-6 周）与本项目现状、开发者"低侵入"要求精准对位。

**「动态薄本体」= 报告轻量档在 eino-multiagent-lab 的落地形态**：

| 维度 | 含义 | 本项目落点 |
| --- | --- | --- |
| 动态 | 随对话运行持续生长，今天长出来的知识明天 agent 就能查到 | 旁路抽取管线 + Oxigraph 会话图增量写入 |
| 薄 | 种子 schema 固定（5 骨架类）、仅实例填充；向量层/自动门控/bi-temporal 后置（报告轻量档边界） | 最小数据模型（§五）+ 三阶段渐进（§九） |
| 隔离 | 每会话产出进独立 named graph，与主本体物理隔离，可整体摘除 | Oxigraph `GRAPH <…/graph/conv-{id}>` |
| 低侵入 | 对话主链路 0 改动、装配逻辑 0 改动、消息库只读、开关默认关 | 三原则（§六） |

## 二、当前项目实现分析（接入面盘点）

**① 会话运行链路（伴生管线的观察对象，全程不改）**：
- 入口：`backend/internal/api/handlers_runs.go` `runConversation` / `resumeConversation` → `chat.Service.Run` / `Resume`（`backend/internal/chat/runner.go`）。
- 装配：`chat/assembler.go` 按 Agent 配置（模型/工具/记忆/知识库）构建 ADK Runner——伴生开关只是 Agent 配置表的一个新字段，装配层读取后决定是否注册伴生查询工具，属配置增量。
- 执行：`runConsumer.consume` 消费 `adk.AsyncIterator[*adk.AgentEvent]`，事件经 `EmitFn` 走 SSE 到前端；运行结束以 `RunResult` 返回——**这就是伴生 worker 的天然触发点（run 收尾 + 消息库游标）**。
- 持久化：SQLite（`backend/internal/store/`），核心表 `conversation` / `message` / `run_event`（REQ-117 调试事件 `debugPersist` 入库）/ `agent` / `model_connection` 等。**消息表已有完整对话事件流，伴生抽取只读该表即可，无需在链路里埋点。**
- 中断恢复与对比运行（`checkpoint.go` / `RunCompare` 双栏）均复用同一 Run 原语，伴生管线对其透明。

**② 推理与抽取能力（复用，不新建模型通道）**：
- 推理后端：`backend/internal/inference/adapters.go` cliAdapter 多后端抽象（含 REQ-160 dsh headless 适配器在研），`/api/ontology-llm/generate`（REQ-98）代理已承载「LLM 抽 KG lightweight」方法位——伴生抽取走同一代理，prompt 库与 JSON Schema 结构化输出约束复用 REQ-127~130 M16 沉淀。

**③ 本体/KG 基础设施（分平面，边界清晰）**：
- 构建平面：`backend/internal/ontobuild/` + `ontology/ontology.go`（BuildProxy/RuntimeProxy 代理 Oxigraph 引擎；REQ-110 TTL 即 KG）。
- 知识库侧 KG：`kg_entity` / `kg_relationship` / `kg_claim` / `kg_community` 表（文档文本抽取，M16 已交付）——**伴生图不进这套表**（来源不同，避免混淆 D-O19 边界）。
- 消费平面：第五栏「消费与审计」按 D-O19 定案只展示本体 TTL 装载来源；伴生图属**第三来源（对话）**，走资产栏独立页签，来源徽标「对话」（与 REQ-163 徽标机制同构）。

**结论：四层架构所需的底座（L1 事件层=消息库、L3 符号层=Oxigraph、M2 抽取=REQ-98 代理、审计=PROV-O 习惯）项目全部已具备；新建的只有 3 块（伴生 worker、候选确认流、伴生开关），全部在旁路。**

## 五、薄本体数据模型

**种子 schema（5 骨架类，一次性预置，薄版不自动生长）**：

```turtle
@prefix bot: <http://eino-lab/ontology/thin/> .
bot:Concept  a owl:Class .   # 概念（领域实体：Pod、HPA、滚动更新…）
bot:Relation a owl:Class .   # 关系陈述
bot:Event    a owl:Class .   # 事件（带时间性动作/变更）
bot:Source   a owl:Class .   # 来源（会话/消息/文档）
bot:Agent    a owl:Class .   # 参与智能体/用户
```

**会话图（named graph 隔离 + 失效化而非删除）**：

```turtle
GRAPH <http://eino-lab/graph/conv-abc123> {
  <…/e1> a bot:Concept ; rdfs:label "Pod 扩容" ;
      bot:extractedFrom <…/msg-42> ; bot:confidence 0.86 ;
      prov:generatedAtTime "2026-09-26T00:00:00Z" ;
      prov:wasGeneratedBy <…/activity-extract-17> .
  <…/e1> bot:relates <…/e2> .
  <…/e0> bot:invalidAt "2026-09-26T00:00:00Z" .  # 矛盾旧边失效化，保留可查历史
}
```

设计要点：①构建平面 spec_json 与主本体 TTL **完全不接触**——伴生图只存在于消费平面（Oxigraph named graph），不产生第二个影子真相源；②三元组自带溯源（`extractedFrom`/`prov:wasGeneratedBy`），满足报告"一切提升带溯源"原则；③低置信度候选只进候选表不入图——对齐报告"低置信信息仍可检索但不影响图"的双存储共生原则的薄版近似。

## 六、低侵入三原则（影响面核对）

| 原则 | 措施 | 影响面 |
| --- | --- | --- |
| 旁路管线 | worker 独立 Go 模块，只读 `message` 表+消费 Run/Resume 收尾事件，不进 Eino ADK run 链路 | 对话主链路/SSE 契约 **0 改动** |
| 可选开关 | Agent 配置页「伴生本体」开关默认关；开启才触发抽取与伴生图查询 | 运行装配仅配置项增量 |
| 产物独立 | 候选表/会话图/审计独立，`DROP GRAPH` + 清候选表即整体摘除，停开关即静默 | Oxigraph 引擎 0 改动；前端 1 页签+1 开关 |

## 七、报告六大风险 → 薄版对策

| 报告风险 | 薄版对策 |
| --- | --- |
| R1 本体漂移/词表爆炸 | 种子 schema 冻结（5 类），类型发现 P3 前不开放——薄版结构性免疫 |
| R2 三元组幻觉 | LLM 只做候选生成，入图必经人工确认（人即门控）；抽取消耗走 REQ-98 代理可控 |
| R3 冷启动 | 薄版无门控预热问题（人工确认不依赖证据积累）；混合检索兜底天然存在（dense 为主） |
| R4 矛盾与时序 | 矛盾检测入候选确认流（同实体新断言提示冲突）；失效化而非删除 |
| R5 隐私治理 | 伴生图会话级隔离可整体摘除；PROV-O 全程审计；开发者数据不出本地 Oxigraph |
| R6 反馈稀疏 | 薄版不依赖反馈信号（人工确认即监督），无此风险 |

## 八、实施价值与项目定位

- **教学价值**：动态本体从论文概念到可操作工程形态的完整最小样本（抽取→确认→入图→查询），与平台"学习智能体构建"定位一致。
- **能力价值**：智能体获得跨会话概念级记忆雏形（P2 起可反查伴生图），为 REQ-103 模式 B（对话式本体构建）提供工程前奏。
- **不动存量**：智能体构建/运行/调试/对比四大既有能力零回归风险（旁路 + 默认关）。

## 十一、优化路线修订（v2.3，2026-09-29，REQ-194 立项）

> 背景：REQ-170 P1/P2 交付后的代码级复盘发现**已实现面与 §一 价值主张存在差距**（召回仍是词法匹配，恰是本方案要解决的"隐式召回失败"本身）。开发者指令「分析当前优化伴生本体方案是否有更好的方式」→ 评估结论=**旁路薄本体骨架保留（低侵入/隔离/溯源三项结构性优点经实践验证），优化主轴自原 P3（自动门控/类型发现/bi-temporal）换轴至「召回增强 + 抽取时实体对齐 + 评估基准」**，两批次六项，随 REQ-194 立项（01 §3.9，挂 M34）。

### 11.0 归属修正

伴生本体需求归属自 03 本体需求修正至 **01 智能体 PRD**（开发者 2026-09-29 拍板）。依据：①伴生为 per-agent 能力——开关/抽取连接覆盖/领域提示/自动阈值均为 agent 表属性（REQ-187 确立）；②消费面在对话链路与智能体侧管理（REQ-189 页签、REQ-193 侧板一级入口），而非本体工程平面（构建/资产/运行不承载伴生数据）；③D-O19 定位伴生图为第三来源（对话），本体模块仅保留全量管理面展示位。REQ-170 存量交付语义不变（03 §2.13 保留并加注），后续演进（REQ-194 起）在 01 排期。

### 11.3 批次一：低垂果实（详设）

**①抽取时实体对齐（extraction-time alignment）——治 G2/G3，REQ-187 自动阈值能安全开的前提**

- 抽取前 `ExtractNew` 经 `SelectLabels(convID)` 拉该会话已有实体标签清单（引擎不在位/空图=清单为空，走现行为，不新增依赖）；
- `companionPrompt` 追加约束节：「本会话伴生图已有实体清单：[…]。抽取规则：新事实涉及清单中的实体时**必须沿用清单原名**（含后缀与写法）；清单实体被进一步刻画（新增关系/定义修正）时同样沿用原名；仅确属新实体才新造名，且新造名不得与清单实体同义近似」；
- 防膨胀：清单 >80 标签时按 slug 前缀聚类取样截断并注入注记；`SelectLabels` 失败降级为无清单抽取（低侵入原则：失败仅日志）；
- 候选元数据：`CompanionCandidate` 增 **aligned 标记**（对齐已有实体/新造），伴生管理列表徽标呈现——人工裁决提速，重复率可观测；
- 改动面：`service.go`（清单注入与标记落库）、`sparql.go`（复用 SelectLabels 零改）、候选表加列（迁移号实现时顺延）、前端徽标。

**②召回增强（向量主 + 词法兜底 + 2 跳邻域）——治 G1，兑现 §一 价值主张**

- 三级召回链：a) **向量**——`SelectLabels` 全量标签批量 embedding，与输入向量余弦相似度 topK≤5、阈值 0.35（可调常量）；embedding 连接取**全局默认**（GetDefaultConnection，REQ-46 既有机制，不新建伴生专属配置）；未配置或调用失败→b) **词法兜底**（现 `recallEntities` 原样保留）；两路命中**合并去重**（向量优先占坑，词法补位）；
- **2 跳邻域**：命中实体边查询扩 bot:Relation 边节点两跳（subject→edge→object→edge2→other，SPARQL 属性路径或两级 JOIN），每实体边总量限流 ≤8，2 跳边标 `hop=2` 注入格式不变（entityHit 结构）；
- 进程内标签向量缓存（会话图写入时失效该会话缓存）——图标签稳态，避免每轮全量重算；
- retrieval 事件明细增 **match 字段**（vector / lexical / 2hop）——前端过程面板如实呈现召回来源（诚实原则）；
- 降级链：embedding 失败静默降级词法 + 日志（与 KB 召回同口径，不发 run.warning）；两路全空=空上下文不阻断主链路；
- 改动面：`retrieval.go`（召回编排重写）、新 embedding 助手（复用 kb 侧 embedding 调用通道）、`sparql.go`（2 跳查询函数）、chat 侧零改动（CompanionSource 接口不变，match 字段走明细 map 透传）。

**③分窗抽取——治 G4**

- `ExtractNew` 内分窗：每窗 ≤16 条消息且 ≤8k 字符（先到为准）；逐窗抽取（同连接/同 hint），上一窗**新造实体名追加进下一窗清单**（与①共用清单机制，跨窗归并）；
- 单次触发最多处理 3 窗，超出部分游标停在第 3 窗末消息——超长积压由后续 Run 收尾自然续抽（游标语义不变）；
- 失败语义：某窗 LLM 失败→中止后续窗、游标停在上一成功窗末（可重试），失败仅日志（低侵入三原则不变）。

### 11.4 批次二：补锚点

**④评估基准——治 G5，后续一切优化（含原 P3）的量化锚**

- 资产形态：`backend/internal/companion/evaldata/`——种子会话 3 段（运维/医学/通用各 20~30 轮，**刻意埋同义改述与跨距离回指**——正对 G1 场景）+ 问题集 15 条（每条标注期望命中实体与关系）+ 跑分器（go test 形态，build tag 隔离手动跑，不进 CI 硬门禁——依赖 embedding 连接在位）；
- 口径：**Recall@5**（检索命中实体 ∩ 期望实体）；抽取环节用**固定 stub 候选**（只评测召回环节，抽取质量另行走人工抽检口径）；三组对比输出：词法基线 vs 向量 vs 向量+2 跳；
- 验收：三组对比数字落档迭代表，证明②收益（预期向量组对同义改述题显著优于词法基线）。

**⑤语义矛盾检测——治 G6**

- confirm 时（含 REQ-187 自动入图路径）拉同主体活跃边全量（`SelectEntityEdges` 已有），与新断言拼 prompt 交 LLM 二分类「冲突/不冲突」（复用抽取连接；冲突才走 invalidAt 失效化）；

- 成本：仅 confirm 时一次小 prompt（入图低频操作，可接受）；判定结论落候选表 note 可审计。

**⑥确认桶聚类——确认疲劳治理**
